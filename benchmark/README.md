# benchmark/ —— 测试数据与准确率

> **建议单独指派负责人（不要压在 C 身上 —— C 已经有四件事了）**
> **一句话：没有标签就没有准确率，没有准确率就没有"有效性"的证明。**

---

## 为什么这是最大的瓶颈

方案的硬指标是：

```
Recall    ≥ 90%      （漏报率）
Precision ≥ 85%      （误报率）
≥ 120 个标注样本（目标 150~180）
≥ 15 类缺陷（其中 ≥8 类与凭据相关）
```

**这些数字现在一个都算不出来**，因为：

> ### 当前标注样本数：0

已下载的全是**靶子**（被扫描的对象），**没有一个是标签**（正确答案）：

| 已有的 | 是什么 | 有标签吗 |
|---|---|---|
| CryptoScan 的 `crypto-samples/` | 6 个文件、~873 行（厂商 demo） | ❌ |
| CrySentry 自带的 30 个 jar | 扫描目标 | ❌ |
| OpenSSH 源码 | 扫描目标 | ❌ |

**没有标签 ⟹ Recall/Precision 无从算起 ⟹ 方案的验收指标悬空。**

而且这是**纯人力活**，没有技术捷径，所以最容易被拖到最后然后做不完。

---

## 优先级

### 1️⃣ CryptoAPI-Bench（**最高优先级**）

- 203 个 Java 文件，覆盖 **18 个漏洞类别**
- **自带标签表 `CryptoAPI-Bench_details.xlsx`** ← 这是关键
- 这是唯一能**快速起量**的路：标签是现成的，不用自己标

> 下载后**先确认标签表能对上文件**，再动手做转换。

### 2️⃣ CamBench

- `CamBench_Cap`（合成）+ `CamBench_Real`（真实项目）
- 质量更高，但**要自己整理标签**

### 3️⃣ 自建样本

前面两个不够数的话，自己写/收集。**但这最慢，尽量少用。**

## 标签格式

标签也要统一，建议放 `benchmark/labels/`：

```json
{
  "file": "src/auth.py",
  "line": 20,
  "algorithm": "RSA",
  "usage": "signing",
  "risk": "shor",
  "expected_severity": "high"
}
```

**标签的字段要和 `core/schema/` 对齐** —— 否则算指标时又要做一次转换。

---

## ⚠️ 算指标前必须先定「计数单位」

这是最容易出错的地方。看实测数据：

| 工具 | 原始结果 | 去重后 | 按什么去重 |
|---|---|---|---|
| cbom-scan | 171 处命中 | **14** | 按「算法」 |
| CryptoScan | 110 条 | **45** | 按「文件+算法」 |
| CrySentry | 8 条 | **3** | 按「类+敏感API」 |

**三家对"这算一条还是三条"的答案都不一样。**

如果我们的输出是 45 条、标签是 14 条，那 Recall 算出来是多少？
**分母不一致，这个数字就是假的** —— 而且答辩时如果被问到会很被动。

统一格式已经定了口径：

> **一条 = 一个 (文件, 算法, 用途) 组合**（见 `core/schema/README.md`）

**标签也按同一口径标。** 这样才可比。

## 指标怎么算

```
                    我们报出的、且在标签里的
Precision  =  ─────────────────────────────────
                    我们报出的全部

                 标签里有、且我们报出的
Recall     =  ─────────────────────────────
                    标签里的全部
```

**汇报时要说清楚口径**：是按条算、按文件算、还是按算法种类算。
三种算法不同、数字不同 —— **说清楚比数字好看重要**。
