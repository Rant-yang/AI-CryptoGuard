## §2：能力和数值目标

| 项目 | 原方案要求 |
|---|---|
| 证据与语言 | 源码、配置、依赖等至少 **3 类安全证据**；第一阶段稳定支持 Python、Java；结果给位置、证据、风险解释与建议 |
| 样本与类别 | **≥120** 个标注样本、**≥15** 类密码安全问题，其中密码/凭据管理缺陷 **≥8** 类 |
| 检测指标 | 总体 Recall **≥90%**、Precision **≥85%**；必须说明样本范围、真值和计数单位 |
| 用途与迁移 | 区分加密、签名、密钥交换/封装、Hash/MAC/KDF、身份认证/证书；RSA/ECC/SM2 等公钥用法给与实际用途匹配的 PQC 建议 |
| 修复与时间 | 典型问题可生成修复建议并复扫验证；普通中小规模样本平均本地检测目标 **≤30 秒**，云端模型时间另计 |

类别清单还包括固定 IV、Nonce 重用、弱随机、硬编码密钥、API Key/Token、
密钥复用、生产/测试凭据混用、证书验证绕过、不安全 TLS、密钥撤销后使用等。
**实现一条规则与证明该类别检出效果是两件事。**

## §3、§7–§10：系统怎么作出结论

1. 第三方扫描工具与自研能力分开说明；CryptoScan、cbom-scan 和 CrySentry 的
   底层扫描不表述为团队自研。统一 Finding 把多工具证据挂到可追溯的问题上。
2. AI 负责不确定的业务语义（例如某次 RSA 调用究竟用于签名还是密钥交换），
   **确定性密码事实由本地规则回答**。输出要结构化，判断须有 `evidence_refs`
   指向已有证据，不能凭空补来源。
3. **禁止**把 `RSA` 固定映射到某一种 PQC 算法。先确认实际用途：签名路线与
   KEM/密钥协商路线不同；用途不能确认时保留条件性候选，不伪称已决定。
4. Repair→Verify 至少选 **3 类**可验证问题，补丁之后要做语法/构建或测试、
   重新扫描，并说明未覆盖的业务兼容风险。

本仓库当前使用 [v0.2 契约](../core/schema/CONTRACT_V0.2.md) 和
`core/rules/` 实现这些原则；方案早期 JSON 例子不覆盖后续契约演进。

## §19：安全与隐私底线

- `workspace/`、`.env`、用户上传、原始扫描结果和可逆匿名映射不得提交。
- 真实 Key/Token 不写日志；凭据发现默认只留指纹或遮蔽结果，报告不展示原文。
- 云模型请求先经 `ai/redact.py` 的白名单脱敏。本机绝对路径、疑似密钥、
  上游 `raw` 原文不直接出网。公开/自有代码可用脱敏后的 `full` 上下文；
  真实第三方代码用 `shape`，只发送调用形状。云端 AI 由用户显式开启。
- 临时扫描任务可删除；报告中的敏感内容默认遮蔽。
