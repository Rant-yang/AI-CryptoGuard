# Java `Cipher.init` 用途证据复验（2026-10-18）

## 为什么补这一条证据

仓库自带的公开 `examples/java_deep_demo/Demo.java` 第 11 行创建
`AES/ECB/PKCS5Padding` Cipher，第 12 行对**同一个局部变量**调用
`cipher.init(Cipher.ENCRYPT_MODE, spec)`。此前扫描结果只携带第 11 行的
`getInstance` 证据；在仅发送 API 调用形状的 AI 模式下，模型据此保守回答
`usage=unknown`。它没有得到判断加密模式所需的第 12 行证据。

`core/usage_evidence.py` 现在只对字面量 `AES/ECB/...` 且同一局部变量在
20 行内出现 `Cipher.init(Cipher.ENCRYPT_MODE, ...)` 的情况，附上两条
`local-literal` 证据：`Cipher.getInstance` 和 `Cipher.init(ENCRYPT_MODE)`。
源码、参数和密钥值不进 Finding；`ai/redact.py` 只允许这两个固定调用形状
进入云端请求。注释、字符串伪调用、不同变量及纯 `getInstance` 的情况均
有离线反例测试。这个规则**只证明配置为加密模式**，不证明 `doFinal`
执行、数据已加密、运行分支可达或跨方法别名成立。

## 同一个公开样例的前后对照

| 输入 | AES-ECB Finding 的本地证据 | AI 用途 | 引用 |
|---|---|---|---|
| 补证据前 | CryptoScan 第 11 行、CrySentry 第 11 行 | `unknown` | `E1` |
| 补证据后 | 另加 `Cipher.getInstance` 第 11 行、`Cipher.init(ENCRYPT_MODE)` 第 12 行 | `encryption` | `E1`、`E3`、`E4` |

两次都是真实 DeepSeek 兼容 API 调用，使用 `--ai-context shape`；后一次
模型的理由明确引用 E4 的 `Cipher.init(ENCRYPT_MODE)`，只说“初始化为加密模式”。
公开样例不含真实凭据。本次结果仅验证**一条公开样例的证据链**，不代表
AI 语义准确率或独立测试；当前 28 条批次的人工盲审仍须单独完成。
