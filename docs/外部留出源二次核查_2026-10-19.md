# 新外部留出来源核查：CCA-Droid 与 CryptoScout 工件（2026-10-19）

目的：寻找未用于调规则、带源码和可核实逐例真值的新样本，供正式 `(文件, 算法, 用途)` 同口径独立留出。**本页只做来源审计，不报告本项目新的 P/R。** 第三方文件均在仓库外，不随匿名源码包分发。

## 1. CCA-Droid 扩展数据集

来源：[作者仓库](https://github.com/AndroidSeclab/CCA-Droid)，本次核对的 `HEAD=e29928612ad57613473a25481635e815e19f5b32`。`dataset/` 含 114 个 Java 文件、11 个 APK，Java 分属 11 个目录：`ecbcrypto` 7、`encryptandmac` 7、`insecureasymmetriccipher` 19、`insecureoperationmode` 7、`insecurepadding` 18、`predictablecryptographickey` 1、`shortmackey` 16、`staticinitializationvector` 11、`staticsalts` 10、`untrustedprngiv` 9、`untrustedprngkey` 9。与本地 CryptoAPI-Bench 的 203 个 Java 文件相比，这 114 个文件无同名或逐字节相同文件；这**不等于**语义独立。

`untrustedprngkey` 的 9 个文件中，7 个已用于[首次独立专项与同集回归](CCA-Droid弱随机密钥首次对照_2026-10-18.md)，另 2 个跨文件案例在那次预注册中排除。不能再把这组称为全新独立集。其余目录多数标的是 IV、padding、MAC 组合等**误用**，不自动等同本产品的算法/量子风险 Finding。文件/目录名也泄漏答案，评测前必须匿名化。作者仓库未见 SPDX 许可证与可直接用于我方 `(文件, 算法, 用途)` 的逐例标签；若采用未碰过的子集，先人工冻结具体文件、正负标签、作用域及匹配规则，再扫描。不能只凭文件名 `Corrected` 生成真值。

**逐文件反例（2026-10-19 再核）：** `dataset/insecureasymmetriccipher/InsecureAsymmetricCipherCorrected1.java` 虽以 `Corrected` 命名，源码仍有 `KeyPairGenerator.getInstance("RSA")` 与 `Cipher.getInstance("RSA/ECB/OAEPwithSHA-1andMGF1Padding")`。它可以是“原基准的弱参数/填充误用已修正”，但不能同时作为“本产品无需提示 RSA 量子迁移”的负例。该目录 19 个文件不能按目录名和 `Corrected` 后缀直接换算为我方全系统同口径 P/R；必须先逐文件审核实际算法、用途及风险定义。`CamBench_Real` 现有 34 条则全是负标签，单独使用无法形成 Recall 分母。

## 2. CryptoScout Zenodo v4：不能直接作为新留出集

来源：[Zenodo DOI 10.5281/zenodo.22971067](https://zenodo.org/records/22971067)，2026-09-26 发布的 `CryptoScout_upload.zip`，下载大小 221,930,234 字节，MD5 `e67321b84d4c548f0b0ee68094b1f387` 与发布页一致。页面称有五套 ground-truth benchmark；实际 ZIP 中可见：

| 部分 | 实际内容 | 本项目处理 |
|---|---|---|
| `cambench` | 623 Java + 459 YAML | 623 个 Java 与我们已有 CamBench 在统一换行后 **623/623 相同**；不是新样本 |
| `ApacheCryptoAPI-Bench` | 10 个预编译 JAR | ZIP 内未见这些 JAR 对应的逐例真值或源码；不能把工具输出当标签 |
| `CryptoAPI-Bench` / `MASC-MinimalFlaws` | 各一个 JAR | 未见可核对的逐文件源码/标签；不能仅凭目录名报 P/R |
| `OWASP-Benchmark` | 一个主 JAR、两个依赖 JAR | 不能把旧 OWASP 家族重新包装成新留出 |

更重要的是，CamBench 459 个 YAML 只有 **453 个与我们已有版本在统一换行后相同**；另 6 个只翻转了 `crypto-usage.violation` 真值，没有附理由：

- `fieldsensitivity/.../falsepositive/smallkeysize/SmallKeySize1_meta.yaml`：false → true
- `fieldsensitivity/.../falsepositive/staticiv/StaticIv1_meta.yaml`：false → true
- `flowsensitivity/.../truepositive/staticiv/StaticIv1_meta.yaml`：true → false
- `interprocedural3/falsepositive/brokenhash/BrokenHash1_meta.yaml`：false → true
- `mixedsensitivities/contextpath/falsepositive/smallkeysize/SmallKeySize2_meta.yaml`：false → true
- `objectsensitivity/.../falsepositive/brokenhash/BrokenHash1_meta.yaml`：false → true

这些值还与路径中的 `falsepositive/truepositive` 相冲突。**不能擅自选一版当真值**；只有查清上游修订原因或独立审阅对应源码，才能使用这些条目。该工件不是现成可复用的全系统新考卷。

## 结论与下一步

这次核查没有找到一套“新、足量、源码＋逐例标签齐全、可直接按我方单位评分”的外部数据。正式同口径独立留出仍缺，不能用既有开发集、重包装的 CamBench 或未标注 JAR 冒充。

可行动的最小方案：从 CCA-Droid **未参与此前 7 例调规则**的目录挑选与产品实际覆盖一致的类别，先由团队读源码、冻结逐文件算法/用途/正负标签及排除理由，匿名化后再首轮扫描；这可以增加新的专项外部证据，但数量和类别不足时仍须如实称为“专项诊断”，不能冒充全系统 120+ 留出结果。另找可验证的真实项目和带逐例人工标签的数据，优先于继续堆检测器输出。
