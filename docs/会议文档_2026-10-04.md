# §2　为什么"一直没测过"

> 这一节很重要，因为它决定你怎么读 §4 那些数字。

## 2.1 「能跑」和「达标」是两条不同的线

我们 9-29 分工时定的验收标准是这样的：

| 人 | 3~4 天后要能拿出来 |
|---|---|
| **A** | "给我一个项目路径，我能输出**统一格式**的问题清单了" |
| **B** | "AI 能吃进清单，并返回**结构化的**判断和建议了" |
| **C** | "A 和 B 能**串起来**跑通了，而且我能**算出准确率**" |

**前两条，A 和 B 都做到了。** 这是真的 —— 端到端跑通、界面能看、中文报告能出。

**问题在第三条的后半句：「算出准确率」。**

A 和 B 交付的是「**这个系统能不能跑**」，
而「**这个系统准不准**」是**另一个问题** —— 它到今天才有答案。

## 2.2 为什么「准不准」拖到今天

不是忘了，是**在数据到位之前，这个数根本算不出来**。

要算 Precision/Recall，需要**一批有标准答案的代码** ——
也就是得先知道"这段代码到底有没有问题、是什么问题"。这叫**标注样本**。

而标注样本数**一直是 0**。`benchmark/README.md` 里原来白纸黑字写着：

> 当前标注样本数：**0**。这是纯人力活，没有技术捷径。

于是链条是这样的：

```
没有标注样本
    ↓
算不出 Precision / Recall
    ↓
无法证明"有效性"
    ↓
但——系统本身是能跑的，Demo 是能演示的
```

**所以 A 和 B 没有任何做错的地方。** 他们那条线是完整交付的。
**缺的是「测量」这一环 —— 而这一环从头到尾都是 C 的活，今天才做完。**

> 换句话说：**这不是"发现你们做得不好"，是"终于能把分数打出来了"。**

方案 §2.2 / §2.3 是**我们一起过过的**，这里只做提醒：

# §3　今天做完了什么

> 这一整节都是新的，之前没跟你们说过。

## 3.1 转折点：这类测试数据是**现成的**

今天做了一次调研，结论是：

> **"密码 API 误用检测"这个方向，学术界已经做了好几套公开的、人工标注好的测试集。
> 我们不需要自己手搓 120 个样本。**

一共找到 **4 套**，合起来 **1411 条标签**，覆盖 5 种语言：

| benchmark | 语言 | 标签数 | 正 / 负样本 | 标签形式 | 泄漏风险 |
|---|---|---|---|---|---|
| **CryptoAPI-Bench** | Java | 203 | 180 / 23 | 目录名即类别 | 🔴 严重 |
| **CamBench_Cap** | Java | 25 | 16 / 9 | 目录名 + `Corrected*` | 🔴 严重 |
| **CamBench_Real** | Java | 34 | 0 / **34** | yaml（**带行号**） | 🟢 无 |
| **LLM-CMT** | C/C++/Go/Java/**Python** | 1149 | 973 / 176 | `labels.csv` 自由文本 | 🟡 轻微 |
| | | **1411** | | | |

**顺带解决的两件事：**

- **Python 有了**（LLM-CMT 里有 245 条 Python）—— 之前这是空白；
- **负样本有了** —— 只知道"哪些是漏洞"算不出 Precision，
  还得知道"哪些是干净代码"。上表里的 242 条负样本就是干这个的。

> **注意「泄漏风险」那一列** —— 下面 3.2 专门讲，这是今天踩到的第一个坑。

## 3.2 陷阱一：这些 benchmark 的**文件名直接就是答案**

**不处理的话，我们所有指标都是假的。**

这些 benchmark 是这样命名的：

```
src/main/java/org/cryptoapi/bench/brokencrypto/BrokenCryptoABICase1.java
                  ↑↑↑↑↑↑↑↑↑↑↑ 包名=类别      ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑ 类名=类别

Dsub/crawl/nomisuses/                             ← 这个目录名意思是"这里全是干净样本"
CamBench_Cap/basic/ecbmode/CorrectedEcbMode.java  ← Corrected = "这是正确写法"
```

**问题在哪**：我们的 `ai/redact.py`（B 写的）在发给大模型前会脱敏，
但它**保留文件名**（`basename(path)`）。

**这在生产环境是完全正确的** —— 用户当然要知道是哪个文件有问题。
但拿它跑 benchmark 就出大事了：

> **文件名把答案直接递进了提示词。大模型照着文件名念，就能"检测"出来。**

跑出来会很好看，而且**一被评委问一句就崩**。

**解决办法：两套模式，不是改产品。**

| | 文件名 | 为什么 |
|---|---|---|
| **生产管线** | **保留** | 用户需要知道问题在哪个文件 |
| **benchmark 跑分** | **匿名化** | 不然失去意义 |

匿名化必须改**三个地方，缺一不可**：

1. **文件名** —— `BrokenCryptoABICase1.java` → `f0001.java`
2. **目录名** —— `brokencrypto/` → `d003/`
3. **文件内容** —— `public class BrokenCryptoABICase1` 和
   `package org.cryptoapi.bench.brokencrypto;` **都写在源码里**，光改路径不够

**但有一处故意不动**：**字符串字面量**。

```java
Cipher.getInstance("AES/CBC/PKCS5Padding")
                    ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑ 这是扫描证据本身，改了就没得扫了
```

规则是：**标识符清掉，注释清掉，字符串留着。**

> 代码在 `benchmark/anonymize.py`。自检验证两件事：
> **原树里 195 个泄漏路径 → 匿名化后 0 个**，**并且 353 个字符串字面量一个没被动过**。

## 3.3 陷阱二：这些 benchmark 测的**不是我们在做的事**

**这是决定一的核心。**

打个比方：

> 这些 benchmark 是给「**密码 API 误用检测器**」出的考卷，
> 考的是「**你把参数写错了没有**」—— 静态 IV、可预测的随机种子、没关的流。
>
> 而我们做的是「**抗量子迁移**」工具，
> 回答的是「**你的算法撑不撑得过量子计算机**」。

**两个完全不同的轴。**

具体例子：CryptoAPI-Bench 有个类别叫 `staticinitializationvector`（静态 IV），
考的是"你有没有给 IV 传一个固定的值"。**这跟量子计算一点关系都没有。**
我们答不出来，**不是我们漏了，是这题本来就不在我们的考卷上。**

CryptoAPI-Bench 的 18 个类别里，**只有 6 个落在我们的轴上**：

| 落在我们轴上（要算） | 不在我们轴上（不该算） |
|---|---|
| `brokencrypto` 经典攻破的算法 | `staticinitializationvector` 静态 IV |
| `brokenhash` 经典攻破的哈希 | `staticsalts` 静态盐 |
| `brokenmac` MAC 误用 | `predictableseeds` 可预测种子 |
| `insecureasymmetriccrypto` 量子脆弱公钥 | `credentialinstring` 硬编码凭据 |
| `ecbcrypto` ECB 模式 | `dummycertvalidation` 证书校验绕过 |
| `pbeiteration`（部分） | …… 共 12 类 |

**所以我们做了一张「裁定表」**，把每家的每个类别逐条判定为：

- **范围内** —— 在我们的考卷上，算进指标
- **部分范围内** —— 算法层面能比，参数层面不能比
  （例如 `pbeiteration`：我们只对 PBKDF2 这个算法有话说，不校验"多少轮算够"）
- **范围外** —— 不在我们考卷上，**不进 Recall 分母，但必须如实报出来**

最终裁定：**范围内 30 个类别 / 部分范围内 10 个 / 范围外 79 个**。

> ⚠️ **一条刻意的设计**：裁定表遇到**不认识的类别会直接报错**，
> 不允许"不认识的 = 范围外"这种默认降级。
> 因为那正是让分母**悄悄失真**的路 —— 少算几条谁都发现不了。

**范围外的类别不会消失**，`eval.py` 每次都会打印出来。
**把范围藏起来只报好看的数字，就是造假。**

## 3.4 陷阱三：**「一条问题」到底怎么数**

三家工具对"这算一条还是三条"的答案**完全不一样**。实测：

| 工具 | 原始结果 | 去重后 | 按什么去重 |
|---|---|---|---|
| cbom-scan | 171 处命中 | **14** | 按「算法」 |
| CryptoScan | 110 条 | **45** | 按「文件+算法」 |
| CrySentry | 8 条 | **3** | 按「类+敏感 API」 |

**分母不一致，算出来的数字就是假的。**

统一口径：**一条 = 一个「(文件, 算法, 用途)」组合**。

> 小陷阱：上游会给**合并名**（如 `DES / 3DES`）。评测时要拆开，
> 命中任一即算匹配 —— 不拆的话，"既报了 DES 又报了 3DES"反而会被判成"没报 DES"。

## 3.5 于是建了四个模块

```
benchmark/
├── scope.py       ① 裁定表：类别 → 我方轴（范围内 / 部分 / 范围外）
├── anonymize.py   ② 匿名化：文件名 + 目录名 + 源码内容
├── adapters.py    ③ 适配器：四家标签 → 统一格式，产出 1411 条
└── eval.py        ④ 评测：算 Precision / Recall / F1
```

| 模块 | 干什么 | 类比 |
|---|---|---|
| `scope.py` | 决定**哪些题该做** | 考前划范围 |
| `anonymize.py` | 把答案**从题目上擦掉** | 把卷子上的答案涂黑 |
| `adapters.py` | 把四家**格式不同的答案**统一 | 四份答题卡读成同一张表 |
| `eval.py` | **判卷**、算分 | 打分 |

**数据放在仓库外的 `../_benchmarks/`（89MB），仓库里只有我们自己写的代码。**

## 3.6 「自检可证伪」是什么意思

四个模块每个都带自检。这里的"自检"不是"跑一遍没报错"，
而是**验证一个能被推翻的事实**：

- `scope.py` 自检会**去问规则库**"你对这个算法有没有话说"再交叉核对 ——
  **不是复述一遍自己的表**；
- `anonymize.py` 自检两头都要过：**泄漏词必须清零**，
  **而且字符串字面量必须一个没动**（否则把文件清空也能"通过"）；
- 有一处专门加了这条：**"比对 0 条"本身算失败**。
  因为之前真发生过"路径分隔符不匹配 → 检查悄悄退化成空断言 → 却报 PASS"。
  **空断言比没有断言更危险，它给人"检查过了"的错觉。**

**为什么值得说**：答辩时评委爱问"你怎么证明数字是真的"。
**"我们的自检可证伪，抽掉正确裁定它会报错"—— 这比数字本身更有说服力。**

| **合计** | **1411** | **533** | **636** | **208** | **24.8%** | **37.9%** |


## 4.2 这几个数**必须带着口径读**

**范围外正样本 636 条，一条都没进上面的分母。**
这不是藏起来的，是 `scope.py` 逐条裁定"这题不在我们考卷上"的结果，
而且 `eval.py` 每次都打印出来。

**Precision 的分母 = 全部 869 条检出**（含 81 条 `safe` 类清点产出，见 4.4）。

## 4.3 Recall 为什么上不去 —— 这是**结构性**的，不是调参能救的

三家 Recall 分别是 **36.3% / 42.9% / 38.1%**。

**三个互相独立的测试集，Recall 全部落在 36~43% 这个窄带里。**
这个一致性本身就是证据：**它不是某个数据集的特例，是方法本身的天花板。**

原因查清了。CryptoAPI-Bench 漏掉的 47 条里，**27 条是这样的**：

```java
// 文件 A
String crypto = "DES";                        // ← 算法名藏在这里

// 文件 B
Cipher.getInstance(String.valueOf(crypto));   // ← 这里只看到一个变量名
```

**正则/模式扫描在结构上就看不见。** 它看到的是 `String.valueOf(crypto)`，
不是 `DES`。要看见它，必须做**跨文件的数据流分析**。

**这不是我们特别差，是这个领域的公认难度。** 文献佐证：
专用研究工具 **Cryptolation 在同一类 benchmark 上也只有 47.4% Recall / 64.33% F1**。

## 4.4 我（C）试过一个自我辩护 —— 它**没站住**，如实记在这里

看到 Precision 只有 24.8%，我第一反应是找解释：

> "会不会是因为我们把**清点产出**也当成误报了？
> 比如我们发现'你在用 SHA-3'，这条本身不是漏洞，只是告诉用户你用了什么。
> 而 benchmark 只标'误用'。这是口径差异，不是我们真报错。"

**听起来很有道理。所以我去实测验证了。**

**结果：只覆盖 81 条，611 条误报里剩下的 530 条还在。**

| 口径 | Precision | Recall | 报出 |
|---|---|---|---|
| A　全部检出（当前口径） | 24.8% | 37.9% | 869 |
| B　只算 broken/shor（最严） | 40.9% | 21.6% | 306 |
| C　只算非 safe | **27.4%** | 37.9% | 788 |

**结论：Precision 低是真问题，不是口径问题。**

**为什么把这个失败写进来**：

1. 这条如果成立，会是个很舒服的解释，讲出来也顺；
   **但它不成立，讲出去被评委一查就是硬伤。**
2. 它正好演示了什么叫"**先有结论再找证据**" —— 我先把辩护编好了，才去验证。
   **正确顺序是反过来。**
3. 所以 §6 里有一条任务就是**查清这 611 条误报的构成**。
   在查清之前，**不要拿 A→C 那 2.6 个百分点去讲故事。**

# §5　还缺什么

## 5.1 三个实测发现的问题

### 🔴 问题 1：同一个 Blowfish 用法被报了两条，而且**结论互相打架**

实测（CryptoAPI-Bench 匿名树），同一条代码产出：

```
Blowfish                                  risk=review   ← 错！
Legacy cipher (Blowfish/CAST5/IDEA/SEED)  risk=broken   ← 对
```

**为什么**：

- 上游 cbom-scan **知道** Blowfish 是坏的，报的是 `Legacy cipher (...)`；
- 上游 CryptoScan 报的是 `Blowfish` —— 而这个**纯算法名**在我们自己的风险表
  （`scanner/normalize.py` 的 `RISK_BY_TYPE`，A 写的）里**没有条目**，
  于是**兜底成了 `review`（待评估）**。

**为什么必须修**：

> 我们整个项目的立论就是"**上游工具会把经典攻破误判成量子脆弱，我们来纠正它**"。
> 结果我们自己**对同一个算法给出了两个互相矛盾的判定**。
> **这是在犯我们声称要纠正的那类错误 —— 而且比上游更糟，因为我们是自相矛盾。**

**根因**：`RISK_BY_TYPE` 缺项。
**修法**：补 Blowfish / CAST / IDEA 等 —— 和 §5.2 的 9 个缺口**是同一批算法**。

### 🟠 问题 2：**同一件事实散在两张手抄的表里**

```
core/rules/zh_map.json   →  quantum_class.by_type   （25 个键）
scanner/normalize.py     →  RISK_BY_TYPE            （25 个键，手抄的）
```

**两张表键完全相同**，全靠人肉同步。而且 `normalize.py` 的注释
**自己承认这是欠账**：

> "C 后续在 `core/rules/` 建立正式规则表后，这里应切换为引用它"

**为什么必须在意**：我们之前吃过"**口径切换要全量重导数字**"的亏。
两张手抄的表 = 定时炸弹：改了一边忘了另一边，
就会出现 **"报告里说 broken、界面显示 review"** 这种没法解释的 bug。

**建议**：这次先两边同时补（保证当下正确），
但**立一个待办**：让 `normalize.py` 改成引用 `core/rules/`，彻底消掉手抄副本。

### 🟡 问题 3：`scan.py --tools-dir` 传相对路径会拼错

实测传 `../_smoke` 会变成 `_smoke\_smoke`，**工具直接挂**。传绝对路径就正常。

**为什么必须修**：**这是会当场出事的那种 bug。**
演示时随手敲一个相对路径，工具就崩了 —— 而且看起来像"我们的工具坏了"。
修起来几分钟。

## 5.2 规则库的 9 个缺口

从 LLM-CMT 的**真实代码**里发现的 —— 这些算法**真的出现了**，我们却答不出来：

```
BLOWFISH   CAST   IDEA   MD2   MD4   NULLCIPHER   RC5   TEA   XTEA
```

查询规则库时返回 `rule-missing`（"我对这个算法没有话说"）。

**同时**是问题 1 的根因，**一次修两件事**。

> 随时可查：`python benchmark/scope.py --gaps`

## 决定二　「37.9%」在答辩里到底怎么讲？

**这个问题比数字本身重要。**

**❌ 不推荐的讲法**：藏着口径，只报一个好看的 36.3%（挑单家最高的报）。

→ 后果：评委一问"**分母是什么**"就崩，而且会被认为**在遮掩**。
**遮掩比数字低更致命。**

**✅ 推荐的讲法**：**把它当成论据，而不是污点。**

> "单靠正则/模式匹配工具，召回率的天花板就在这里 ——
> **这是我们自己实测的（37.9%），也是文献的结论（Cryptolation 47.4%）。**
> **这恰恰就是为什么我们的方案要设计成多源融合 + 数据流分析 + 大模型。**
> 如果我们只做个正则扫描器就宣称 90%，那才是不诚实的。"

**这个叙事还有一组更硬的支撑数据**：

```
869 条检出中：
  · 多源交叉     140 条 —— 同一问题被多个工具共同指认
  · 风险已纠正   281 条 —— 上游工具的判定被我方规则库推翻
```

> **「281 条上游判错了、被我们纠正」—— 这个论点的强度高于 Recall 数字。**
> 因为它直接证明了"**多源融合 + 规则裁决**"这一层的**存在价值**：
> **如果没有我们，这 281 条就是错的。**

**要确认两件事**：
1. 全队认不认这个叙事？
2. **答辩时这段由谁讲？**（建议 C —— 口径和数字都在 C 手上）
