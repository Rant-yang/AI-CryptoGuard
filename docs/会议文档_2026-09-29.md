## 一、开场用一句话说清我们在做什么

照着念：

> "我们**不自己写密码扫描器**。我们先拿现成的开源工具去代码里找密码相关的问题，
> 然后我们自己做**统一整理**，再让 **AI 来解读**这些证据，最后输出一份人能看懂的
> 报告，包括怎么修、以及怎么迁移到抗量子密码。"

画这张图（就画这个，不要画更多）：

```
   一个代码项目
        ↓
   现成的扫描工具        ← 不是我们写的
        ↓
   我们做：统一整理       ← 我们的第一块工作
        ↓
   我们做：AI 解读        ← 我们的第二块工作
        ↓
   报告 / 修复建议 / 迁移建议
```

**为什么这不算"没技术含量"**：因为三个工具各说各话，而且**它们的结论会互相打架**（第二节有实例）。
把它们对齐、裁决、并给出可验证的指标，这才是我们的作品。

## 二、打个比方：这个项目就是"给代码做体检"

跟队友解释的时候，用这个比方最省事：

| 项目里的东西 | 体检里的对应 |
|---|---|
| 待扫描的代码项目 | 来体检的人 |
| cbom-scan / CryptoScan | **快速筛查**（像验血，几分钟出结果，先看有哪些"密码零件"） |
| CrySentry | **精密检查**（像 CT，看得深，但排队久，而且**只能查 Java**） |
| 统一格式 | **把所有仪器的结果填到同一张化验单上** |
| AI 解读 | **医生看化验单**，判断这个异常严不严重、要不要治 |
| PQC 迁移建议 | **开药方**（但要**查药典**，不能医生自己编 —— 见第九节） |

这个比方能帮队友立刻明白：**我们不是造仪器的人，我们是开体检中心的人。**

## 六、统一格式（今晚定 v0.1，明天会上过一遍）

### 为什么必须有这个东西

因为**三个工具现在各说各话，连"一条问题"怎么数都不同**。这是实测数据：

| 工具 | 原始结果 | 去重后 | 按什么去重 |
|---|---|---|---|
| cbom-scan | 171 处命中 | **14** | 按"算法" |
| CryptoScan | 110 条 | **45** | 按"文件+算法" |
| CrySentry | 8 条 | **3** | 按"类+敏感API" |

**三个工具对"这算一条还是三条"的答案都不一样。**
如果不统一，最后算"识别率 90%"就是一笔糊涂账 —— 分母是多少都说不清。

### v0.1 草案（给队友看这个就够）

```json
{
  "file": "src/auth.py",           // 文件（相对路径）
  "line": 20,                      // 行号
  "algorithm": "RSA",              // 什么算法
  "usage": "signature",            // 用途：签名/加密/密钥交换/哈希
  "risk": "shor",                  // 风险等级（五档，见下）
  "severity": "high",              // 严重程度
  "evidence": [                    // 证据：谁发现的、在哪
    {"tool": "cbom-scan", "line": 20},
    {"tool": "cryptoscan", "line": 20}
  ]
}
```

**三个关键点，明天要跟队友强调**：

1. **`evidence` 是个数组** —— 一条问题可以挂着好几个工具的证据。
   这就是方案里要求的"多源证据"，也是我们区别于单个工具的地方。
2. **`risk` 用五档**：`shor`（量子能破）/ `broken`（已被经典攻击攻破）/
   `grover`（量子削弱）/ `review`（要人工看）/ `safe`（安全）。
   **这个分类直接抄 cbom-scan，因为它是三个工具里唯一分类正确的。**
3. **`severity` 和 `risk` 是"我们系统的判断"，不是照抄某个工具。**
   三个工具给的值不一样，必须由我们裁决（这也是融合层的核心工作）。

### 关于"冻结"

**"冻结"没那么正式**，就是一句话：

> "大家先统一按这个格式写，不要三个人各写各的。"

**建议节奏**：
```

明天   会上过一遍，问"有没有明显问题"
没问题 当场宣布"就按这个写"  ← 这就是冻结
```

**不要**花两天开会研究格式。**先跑起来，比格式完美重要得多。**

## 九、关于密码知识：不用先学，但有一个例外

### 不用先学

你们第一周真正需要的密码知识其实很少：
```
RSA 是什么、AES 是什么、ECB/CBC/GCM 是什么、
key / IV / nonce 是什么、hash 是什么、数字签名是什么、PQC 大概是什么
```

**绝对不要**"三个人停一周先系统学密码学" —— 时间不允许。
正确姿势是**边做边学**：

```
做开发 → 碰到"固定 IV" → 花 20 分钟搞懂 IV → 继续开发
       → 碰到 RSA 迁移  → 花 30 分钟搞懂签名/加密的区别 → 继续开发
```

### 但有一个例外：PQC 迁移这块必须先有共识

**原因**：这是**题目核心**（题目里就有"抗量子迁移"），而且 B 的 AI 模块会**直接用**到它。
如果 B 不懂，他一定会让 AI 输出错误建议。

**开会时花 20 分钟讲清这三件事**（就这三件，讲完就够）：

```
1. ML-KEM  →  用来"加密/密钥交换"（FIPS 203）
2. ML-DSA  →  用来"数字签名"     （FIPS 204）
3. SLH-DSA →  也是签名，是备选    （FIPS 205）

★ 最关键的一条：
   签名和加密不能互换！
   RSA 用来签名 → 换 ML-DSA
   RSA 用来加密 → 换 ML-KEM
   用途不知道 → 就说"暂时不确定，需要先确认用途"

★ 所以：AI 不能自己决定换成什么，必须"先判用途，再查表"。
```

**为什么这条这么重要**：方案文档里明确写了**禁止"RSA → 固定某一种后量子算法"**这种映射。
如果 AI 自由发挥，它一定会写"RSA 换成 ML-KEM"，评委一问"那签名场景呢"就答不上来。

> 好消息：**这个"先判用途、再查表"的逻辑已经写好并跑通了**，
> 在 `_smoke/report_cn.py` 里。可以直接给 B 当模板，他照着填就行。

## 十、三个千万别踩的坑

### 坑 1：让 AI 自由生成"该换成什么算法"

**症状**：B 图省事，直接让大模型输出"RSA 应该换成 ML-KEM"。
**后果**：违反方案硬性规定，评委一问就穿。**这是最容易被抓的失分点。**

**正确做法**：
```
AI 只判断"用途"（签名？加密？）  →  查规则表  →  得到算法
用途判断不出来  →  明确说"暂不给出具体算法"
```

### 坑 2：以为"三个工具都能直接调用就完事了"

**症状**：以为"输入一个路径，三个工具一起跑"。
**后果**：CrySentry **做不到**，它要编译好的 Java 包。

**正确做法**：
- **第一版只接 cbom-scan + CryptoScan**（两个都是"给源码目录就能跑"）
- CrySentry 单独安排，**不作为第一版的要求**

### 坑 3：Python 那边以为"照着 Java 的抄一份就行"

**症状**：以为 CrySentry 是个"Java 扫描器"，抄成 Python 版就好了。
**后果**：严重低估工作量，做不完。

**真相**：CrySentry 背后是一整套**研究级的程序分析引擎**（叫 Tai-e），
不是"一段可以照抄的扫描逻辑"。**"照着它重写一个 Python 版"是不现实的。**

**正确做法**：Python 侧**用 Python 自带的 `ast` 模块写个轻量版**——
能追踪"这个密钥是从哪来的"就够，**不追求和 CrySentry 一样强**。
目标是"**Python 也有独立的证据**"，不是"Python 版的 CrySentry"。

> 补充一个实测事实：cbom-scan **已经覆盖了 Go / Python / JS / Java 四种语言**
> （171 处命中分布在 .go / .py / .js / .java 四类文件里）。
> 所以 Python 不是完全没人管，只是**"浅"**——它只认算法名，不理解上下文。

### A-4　中文报告　`约 0.5 秒`　←　演示的收尾

```cmd
cd /d D:\code_competition\_smoke
python report_cn.py
```

自动读取 `cs.json` 和 `CrySentry\crypto-output\activemq.json`，输出中文报告。

**演示时说什么**（这是最有说服力的一段）：

> 看这一条 —— **MD5**。
> CryptoScan 把它标成「量子脆弱（Shor 算法可破）」，
> 但 **MD5 是被经典攻击攻破的，跟量子计算机没关系**。
>
> 我们没有透传这个结论，而是用规则库纠正了它，
> 并且**在报告里把分歧显式打出来**。
>
> 再看 RSA 和 ECC：同一个算法、不同用途，给的迁移建议不同 ——
> **签名走 ML-DSA，加密走 ML-KEM**；
> 用途判不出来的时候，明确说"暂不给出具体算法"，**而不是猜一个**。
>
> **这就是我们作品的价值所在。**
