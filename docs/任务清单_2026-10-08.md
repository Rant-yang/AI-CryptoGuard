# 任务 1（A）· 合并名拆词

## 是什么

cbom-scan 的 `algo` 字段**不一定是单个算法**，可能是带括号的合并名：

```
Legacy cipher (Blowfish/CAST5/IDEA/SEED)
```

## 为什么是 bug

`scanner/normalize.py:20` 的 `norm_algorithm()` 会把**所有非字母数字去掉**：

```
"Legacy cipher (Blowfish/CAST5/IDEA/SEED)"
        ↓ norm_algorithm()
"LEGACYCIPHERBLOWFISHCAST5IDEASEED"          ← 一坨，谁都不认识
```

于是这条 finding 的 `algorithm_normalized` 变成一坨长串，
**永远匹配不上任何单算法标签**（`BLOWFISH`、`IDEA`……），也匹配不上它的兄弟 finding。

实测代价：**94 条**。而且报告里会出现「算法：Legacy cipher (Blowfish/CAST5/IDEA/SEED)」——
答辩时一眼就知道这不是算法名。

## 改哪里

`scanner/adapters/cbom_scan.py:106-107`

```python
algo_raw = asset.get('algo', '')          # 这里拿到的是合并名
alg_norm = canon_algorithm(algo_raw)      # 这里被压成一坨
```

## 改成什么样

**不是加别名，是拆词。**

`core/schema` 定死的计数单位是「**一条 finding = 一个 (文件, 算法, 用途)**」——
所以这条本来就该**拆成 4 条**（Blowfish / CAST5 / IDEA / SEED 各一条），
各自有独立的 `finding_id`、独立的 `line`。

建议做法（实现由 A 定，但必须满足下面的不变式）：

1. 在 `scanner/normalize.py` 加一个函数，识别 `前缀 (A/B/C)` 结构，返回候选算法列表
   ```python
   split_combined_algorithm("Legacy cipher (Blowfish/CAST5/IDEA/SEED)")
   # -> ['Blowfish', 'CAST5', 'IDEA', 'SEED']
   split_combined_algorithm("AES-128")
   # -> ['AES-128']        ← 没有括号，原样返回
   split_combined_algorithm("AES/GCM/NoPadding")
   # -> ['AES']            ← 这是「算法/模式/填充」，不是多算法，别拆成三个
   ```
2. 在 cbom adapter 里对每个拆出来的算法**各产出一个 ToolGroup**

⚠️ **第 2 条那个坑要小心**：`AES/GCM/NoPadding` 也含 `/`，但它是**一个**算法的参数写法，
拆开就错了。区分办法：**带括号的**（`X (A/B/C)`）才拆，纯斜杠的不拆。

## 验收标准（必须可证伪）

```bash
cd AI-CryptoGuard

# 1) 自检要能证明「拆干净了」——断言的是真实约定，不是复述实现
python scanner/selftest.py

# 2) 跑一次基准，看这两条：algorithm_normalized 里不该再有长于一坨的合并名
python scanner/scan.py <某个目录> -o out/findings.json
python -c "
import json,sys; sys.stdout.reconfigure(encoding='utf-8')
bad=[f for f in json.load(open('out/findings.json',encoding='utf-8'))
     if f['algorithm_normalized'].startswith('LEGACY')]
print('合并名残留:', len(bad))
"
# 期望输出：合并名残留: 0

# 3) 对指标的影响（C 会跑，A 知道数字就行）
python benchmark/eval.py out/bench/_all.json
```

**硬性不变式**：`algorithm_normalized` 里**不允许出现 `LEGACYCIPHER...` 这种拼接串**。
自检里要有一条断言把这件事钉死 —— 否则以后换个工具又会漂回来。

# 任务 2（A）· `type` 不许当算法

## 是什么

`scanner/adapters/cryptoscan.py:122`：

```python
algo_raw = f.get('algorithm') or f.get('type') or ''
#                             ^^^^^^^^^^^^^^^^^^^^^ 病根
```

CryptoScan 有些 finding **没有 `algorithm` 字段**（TLS 配置、证书、硬编码密钥这类）。
代码就**退化成拿 `type` 当算法名**。

## 为什么是 bug

`type` 回答的是「**发现了什么问题**」，不是「**用了什么算法**」。实测漏到报告里的：

| UI 上显示的「算法」 | 条数 |
|---|---|
| Weak PBKDF Usage | 17 |
| Hardcoded Key Size | 5 |
| Certificate Key Usage | 4 |
| Mutual TLS (mTLS) | 4 |
| Certificate Validation Bypass | 3 |
| Hardcoded Encryption Key | 1 |
| 其余（Certificate Chain / Subject Alternative Name / TLS …） | 11 |

**45 条**。其中杀伤力最大的是**展示**：报告和 UI 上会出现「算法：Mutual TLS (mTLS)」，
评委一眼就知道这是拿错字段了。

> 顺带说一句：这个退化是**当初故意写的**（见该文件 docstring：「保持组可聚合」）。
> 动机能理解，但手段错了 —— 代价是把「不是算法的东西」写进了算法字段。

## 改哪里

`scanner/adapters/cryptoscan.py:122`（`to_groups()` 里）

## 改成什么样

```python
algo_raw = f.get('algorithm') or ''          # 不再退化成 type
```

然后处理 `algo_raw` 为空的情况。**这里 A 要做一个选择，但两条路都行，别第三种**：

**方案甲（推荐）· 保留 finding，但如实标出来**
- `algorithm` / `algorithm_normalized` **留空**
- 分组键用一个**明显不是算法**的前缀，例如 `('TYPE:' + type_norm)`
- 打一个 tag `no-algorithm`
- 好处：TLS / 证书 / 硬编码密钥这些线索**留着**——C 正在做的「8 类凭据检测」
  （任务 4）要用它们
- 代价：这 45 条仍然算误报，但至少**不再以假算法的样子出现**

**方案乙 · 直接不产出这类 finding**
- 好处：45 条误报直接消失，Precision 立刻上升
- 代价：**线索也丢了**，而且「X 类问题我们不报」是个口径决定，
  **要 C 拍板，A 不要自己定**

> ⚠️ **不要用 `core/rules/pqc_routing.py` 的 `route()` 来判**。
> C 试过：`route('Mutual TLS (mTLS)')` 返回的是 `rule-missing`，**不是**
> `not-an-algorithm` —— 只有 `Hardcoded Key Size` 这种已收录的才命中 `_NOT_ALGORITHM`。
> 照那个写会白干。

# 任务 3（B）· `evidence_refs`

## 是什么

方案 **§7**（`crypto_competition_project_plan.md` 第 659 行）原文：

```json
{
  "usage": "digital_signature",
  "is_true_positive": true,
  "reason": "...",
  "evidence_refs": ["E1", "E3"]
}
```

> 其中 `evidence_refs` 很重要：AI 的判断必须引用已有证据，不允许无依据自由发挥。

**`E1` / `E2` / `E3` = 这条 finding 的 `evidence[]` 数组里的第 1 / 2 / 3 条。**

不是新发明的编号，就是数组下标（1-based）。

## 为什么

1. **它是方案里的硬指标** —— §15 检查清单第 1640 行：
   `- [ ] AI 输出结构化且有 evidence_refs`
2. **它是「AI 不负责密码学确定事实」这条红线的落地机制**（方案 §8.1）。
   有引用，人才能核对 AI 有没有编。

## 现在差多少

AI **已经在用嘴引用证据了**。看真实产出（`out/findings_ai.json` 第 1 条）：

```json
{
  "file": "CryptoSamples.java", "line": 82, "algorithm": "AES-128",
  "evidence": [
    { "tool": "cbom-scan", "kind": "pattern", "lines": [82], "raw": {...} }   ← 这是 E1
  ],
  "explanation": "……但本次 evidence 中 call_shape 与 call_context 均为空，
                  仅有算法标识与上游大类，无法排除分组密码被用于构造 MAC/认证……"
}
```

这句话说的**就是 E1 的内容** —— 但没有任何结构化引用。
做到位应该是：

```json
{
  "explanation": "……（原文不变）",
  "evidence_refs": ["E1"]
}
```

这条 finding 只有 1 个证据源，所以只能引用 E1。
UI 上「证据（**2** 个来源）」那个数字就是 `evidence[]` 的长度。

## 改哪里

- `ai/enrich.py` —— 输出 schema 与 prompt
- `ai/selftest.py` —— 加断言（见下）

## 验收标准（关键）

**自检必须能失败**，否则 refs 就是装饰。要断言的是**真实约定**：

```python
# ai/selftest.py 里加，伪码
for f in enriched:
    refs = f.get('evidence_refs') or []
    n = len(f.get('evidence') or [])
    assert refs, 'AI 结论没带 evidence_refs'
    for r in refs:
        # 'E1' -> 0, 'E2' -> 1
        assert r.startswith('E') and r[1:].isdigit(), 'ref 格式不是 E<n>: %r' % r
        i = int(r[1:]) - 1
        assert 0 <= i < n, '引用了不存在的证据 %s（该 finding 只有 %d 条）' % (r, n)
```

**三条硬性要求：**
1. 每条结论**至少**有一个 ref
2. ref 必须**落在 `evidence[]` 范围内**（引用不存在的证据 = 自检失败）
3. **不能所有结论都引用 E1** —— 那说明这个字段没有信息量。
   加一条统计断言：refs 的分布里，`E2` 及以上要占一定比例

> ⚠️ 第 3 条容易被忽略。如果 AI 对所有东西都填 `["E1"]`，字段是"有"了，
> 但答辩时被问「这个 E1 到底指什么」就露馅了。

# 任务 5（C）· 口径对称

## 是什么

`benchmark/eval.py` 现在：

```python
tp = len(tp_detail)
fp = reported - tp          # ← 所有没匹配上范围内正样本的，全算误报
```

**Recall 的分母已经剔掉了范围外类别，但 Precision 却把落在这些类别文件上的检出算成误报。不对称。**

## 为什么

我们在一个 `credentialinstring` 文件上正确报出了硬编码凭据 ——
**benchmark 自己也标了这是硬编码凭据**。我们是对的，只是不在评分轴上。算成误报不成立。

## 怎么做

`benchmark/eval.py` 增加一档计数，**两套数字都报**：

- **严格口径**（现状）：范围外文件上的检出计入 FP
- **对称口径**：范围外文件上的检出单独计数，不计入 Precision

> **不许只报好看的那个。** 这与现有规矩一致 ——
> eval 现在就必须如实打印「范围外正样本 627 条未计入任何指标」。
> 藏起来只报好看的，就是造假。

## 注意

**这一条是「怎么讲数字」，不是「把数字变好看」。**
真要把那 191 条变成正分，得靠任务 4 把凭据检测做出来。
