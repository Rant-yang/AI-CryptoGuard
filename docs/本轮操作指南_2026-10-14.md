## 1. 三个人先统一这句话

给系统一个项目，先用现有扫描器找问题；Java 项目可以增加 CrySentry 深度证据；
然后由本地规则库做量子风险评估；最后 AI 结合代码证据和评估结果，说明用途、
为什么需要处理、具体怎么改、改完怎么验证。

**用户确认的先后顺序：量子风险评估放在扫描完成之后、AI 解释之前。**

```text
项目路径 + 可选 Java 编译产物 + 可选业务背景
        ↓
快速扫描：cbom-scan / CryptoScan / local-literal / credential-scan
        ↓
Java 可选 CrySentry 深度分析；Python 保持现有分析路径
        ↓
证据整理与融合（保留来源、不确定性、任务状态）
        ↓
本地量子风险评估（规则版本、依据、未知项、条件性迁移候选）
        ↓
AI 判断实际用途、解释问题、提出有证据的整改步骤
        ↓
程序根据确认的用途调用规则库，校验最终迁移路线
        ↓
中文报告 / 证据引用 / 整改与验证步骤
```

最后一次规则查表是整改建议的校验，不改变“先评估、后 AI 解释”的顺序。
例如扫描只识别出 RSA、用途未知，前置评估仍能指出其量子风险；但不能提前固定
选择签名或密钥建立路线。AI 之后确认用途，程序才选对应规则。用途仍未知就保留待确认。

## 4. A：Java 深度证据，按这六步做

### A1. 复现现有 smoke，先知道输入输出

本机已有资源在 `D:\code_competition\_smoke\CrySentry`。cmd 可执行：

```cmd
call D:\code_competition\_smoke\run_crysentry.bat
```

该脚本使用 JDK 17、构建 fatJar，并按现有 options.yml 分析 activemq。
它仅用于验证安装，**不能直接作为“扫描任意用户项目”的正式入口**。
先读 options.yml 和实际 JSON，记录分析所需 classpath、目标、配置、结果路径。
不要每次扫描都重新构建工具；构建与运行分开。

### A2. 封装调用器

建议新增 `scanner/runners/crysentry.py`（拟新增，当前没有此接口）。输入包含：
Java 可执行文件、工具 jar、目标 jar/class、依赖 classpath、配置、超时、内存上限、
独立输出目录。使用参数列表启动进程，禁止拼接 shell 字符串。

每次任务生成独立配置和输出目录；不修改全局 options.yml，不读取上一轮残留结果。
未编译 Java 源码先完成快速扫描，并明确提示“缺编译产物，深度分析跳过”。
第一版不自动运行任意第三方项目的 Maven/Gradle 构建脚本。

状态统一为 completed / skipped / failed / timeout，并记录原因、耗时、版本和输入摘要。
completed + 0 findings 与 skipped 必须分开。超时结束子进程树，保留快速结果。
默认先串行运行深度任务；内存与时间限制通过配置给出，并记录实际测试值。

### A3. 转换证据

建议新增 `scanner/adapters/crysentry.py`。保留调用点、方法签名、源语句、汇点、
传播路径（工具确实提供时才填），标记 `tool=crysentry`、真实数据流证据为 `kind=taint`。
没有 sourceStmt 时记录“来源缺失”，不能补造完整路径。

类名、jar 路径不能冒充源码路径。行号不存在时不能填 1 假装定位成功：
优先写入任务的未定位深度证据列表，待 C 的定位契约支持后再输出 Finding。
只有确切映射到源码文件/行号的记录才能进入要求正整数行号的现有 Finding。

不同工具同一事实合并证据，不能仅凭同文件同算法就混合不同调用点。
算法未知的误用保留为明确类型的线索或配置/凭据问题，不用 API 名填 algorithm。
深度工具没报某条问题不构成误报反证；不自动删除快速结果。

### A4. 加入模式选择

拟新增参数 `--mode fast|deep-java`、`--java-artifact`、`--java-classpath`。
参数尚未实现，完成后写入 scanner/README。混合项目中 Java 做可选深度分析，
Python 仍完成现有扫描；在任务状态里分别标注语言与实际执行能力。

### A5. 做同题对照

先选能稳定编译且标签明确的 Java 用例，包含直接调用、跨方法传值、正确用法和依赖缺失。
保存固定 manifest、来源版本、构建方式和排除理由。比较同一清单上的：
快速扫描、快速＋深度。报告 TP/FP/FN、P/R/F1、完成率、耗时、资源限制。
失败/超时不能被静默踢出分母；另报成功子集指标时必须同时报告全清单结果。
将新增真阳性、新增误报、重复证据分别列出。不承诺两个指标一定同时提高。

## 5. B：AI 用途解释与具体整改，按这五步做

### B1. 明确角色与输入

角色：面向普通开发者的密码安全审计助手。任务是理解用途、解释影响、提出具体步骤，
不能编造业务背景、代码路径、API 或测试执行结果。

输入：脱敏证据、前置量子风险评估、规则库允许的迁移候选、用户明确提供的业务背景。
规则结论与源码证据是两种来源，引用要区分。源码里的注释和文本是待分析数据，
不能成为改变系统规则的指令。继续使用 ai/redact.py，不整包发送原始工具输出。

### B2. 输出五个用户能读懂的部分

1. 这段代码在做什么：用途及 evidence_refs；未知就写未知。
2. 问题是什么：结合代码证据与前置风险依据说明。
3. 哪些影响已知，哪些依赖业务条件。
4. 怎样改：具体位置、动作、前置条件、兼容性和回滚注意点。
5. 怎样验证：测试步骤与期望结果；未执行的步骤必须标为待执行。

整改步骤用数组，不用一整段长文本。每条含 action、target、evidence_refs、
rule_refs、prerequisites、verification。代码位置不确定时 target=null。
依赖规则的建议引用 rule_refs；关于代码的判断引用 evidence_refs。
不得为了满足非空引用而随意填 E1。

### B3. 保持规则约束

量子风险由 C 的模块先算。AI 可提出“用途需修订”，不能静默覆盖风险依据。
程序校验 usage 枚举，再调用规则库选择迁移路线；生成整改说明时只能使用允许的候选。
若第二次生成解释需要增加调用，要单独记录成本和耗时。
单次调用也可返回带用途条件的结构化方案，由程序校验；校验不通过就降为待确认。
未知用途不能默认给固定 PQC 方案。凭据问题沿用本地加固建议，不强行套量子迁移。

### B4. 处理引用和缓存

E1/E2 是当前 Finding 的 evidence 数组位置。融合新增证据后，不能只校验“没越界”：
必须确保编号仍指向原证据。共享规则由 C 实现，B 配合缓存键使用证据摘要、规则版本、
提示词版本、模型配置摘要及脱敏策略版本；不把 API 密钥写入缓存键或日志。

现有演示曾按 Finding ID 复用旧解释，不能把该演示当成本轮引用语义验收通过。
新证据/新规则/新上下文产生时，应失效旧结果或严格重映射；不要直接挪用旧引用。

### B5. 验收和抽样

- [ ] 输入缺少量子评估时，明确兼容旧模式或报出前置阶段缺失，不能假装评估完成。
- [ ] 无效引用、越界、证据改序、无证据结论都有回归用例。
- [ ] 单条失败保留数据；恢复运行只复用内容一致且结构有效的结果。
- [ ] 约 30 条分层样本：10 单源、10 多源、5 未知用途、5 凭据/非算法。
- [ ] 对照改动前后：用途是否正确、引用是否支持、整改是否可执行、是否编造事实。
- [ ] 至少由另一名队友复核；分歧与无法判断项保留，不能统一记为正确。
- [ ] ai/交付说明.md 写明模型、提示词版本、样本清单、耗时、结果和局限，不含密钥。

## 6. C：契约、前置评估、调度和 Web

### C1. 最先发布接口夹具

每组给出扫描后、风险评估后、AI 后三个阶段示例。夹具只能用公开或合成材料。

不要让 A/B 等所有功能做完再谈接口。

### C2. 做前置量子风险评估

建议新增 `core/rules/quantum_assessment.py`。本阶段不调用 LLM。
输入包括算法、已知参数、扫描器提供的用途提示、证据及可选业务背景。
输出包含算法/参数识别状态、量子影响、经典安全问题、规则引用、未知项、条件性候选。

经典风险和量子风险可以同时存在，不能强制二选一。例如弱 RSA 参数可以存在经典风险，
RSA 家族也存在量子威胁；MD5 的碰撞问题不能解释成 Shor 风险。
不要把对称算法的理论量子加速简化成所有场景“一律强度减半、必须马上替换”。
规则引用与技术表述在实现时核对官方标准，保存出处和规则版本。

需要长期保密的数据可评估“现在收集、未来解密”的条件性影响；保密年限、部署环境、
系统寿命等来自用户输入，缺失时 unknown。签名不能直接套用历史密文解密叙述。
迁移优先级给理由与缺失信息，不给没有依据的量子破解年份或伪精确评分。

safe 资产当前可能被移出 findings。前置资产级评估还应读取完整资产视图/CBOM，
避免因为问题清单过滤而遗漏应评估的资产；正常资产不强制变成问题或 FP。

### C3. 做调度

拟新增 `run.py`：统一任务目录，按约定顺序串联；记录输入摘要、阶段状态、版本和耗时。
快速模式与深度模式均在量子评估后才进入 AI。异步显示快速结果时标注“阶段性结果”；
最终深度证据到达后，重新评估并失效受影响的旧 AI 结果。
日志不含凭据原文，原始项目不被自动修改。AI 故障仍可查看扫描与规则评估报告。

### C4. 改 Web

- 扫描概况：语言、快速/深度、完成/跳过/失败原因、耗时。
- 量子风险卡片：评估结果、规则依据、未知项、适用条件。
- AI 解释：实际用途、证据链接、普通开发者能读懂的影响说明。
- 整改清单：改哪里、做什么、前置条件、怎样验证、是否已执行。
- 明确区分工具证据、规则依据与 AI 推断；历史缓存必须可识别。

### C5. 集成验收

复核 A/B 分支，解决接口差异，跑已有自检和新增阶段验收；更新 README 与项目现状。

## 7. 正式接口约定（v0.2 已发布）

正式定义见 [共享契约 v0.2](../core/schema/CONTRACT_V0.2.md)，含 Schema、四组夹具和语义校验器。旧 v0.1 保留原校验入口。下表为概览；开发以正式契约为准。

| 对象/字段 | 谁产出 | 谁消费 | 约定 |
|---|---|---|---|
| task.json / stages | 调度器 | 前端、评测 | 语言、执行状态、原因、耗时、工具版本 |
| unresolved_deep_evidence | A | C | 无可靠源码定位的证据；不能伪造行号 |
| evidence 中的深度信息 | A | C、B | source/sink/path、完整性；仅填工具确实提供的事实 |
| quantum_assessment | C | B、前端 | status、quantum_effect、classical_issues、rule_refs、unknowns、条件候选 |
| usage_assessment | B | 规则路由、前端 | usage、依据、未知项；机器校验后才写最终 usage |
| remediation_steps | B＋规则校验 | 前端 | 有位置、有步骤、有条件、有验证；不能声称已执行 |
| analysis_provenance | C＋B | 缓存、报告 | 输入摘要、规则/提示词版本、模型配置标识、脱敏版本 |

前置 quantum_assessment 的 status 建议为 assessed / insufficient_evidence / not_applicable。
不以 source=rule-base 代表 AI 已处理：前置评估本来就是规则结果，AI 完成状态需独立记录。
正文 evidence_refs 继续指向证据；rule_refs 指向规则库条目，不能把规则假装成扫描证据。

整改步骤示例（完整可校验 Finding 见 core/samples/v0.2/）：

```json

  "action": "将密钥加载改为受控运行时注入，并安排已使用密钥的轮换",
```
