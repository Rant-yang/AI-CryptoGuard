# 证据用途隔离回归（2026-10-18）

## 修正了什么

同一算法家族在一个文件中可能承担不同用途。此前 CryptoScan 适配层把同文件、同算法的用途摆动统一并入多数用途，导致 `hybrid_crypto.js` 的 ECDH 密钥交换第 13 行与 ECDSA 签名第 104 行进入同一个 Finding。AI 可能因此把交换证据当成签名依据，进而给出错误的 PQC 路线。

现在，RSA/ECC 等公钥家族的具体用途不再跨桶合并；cbom-scan 的家族级 `ECDSA / EC` 只在匹配文本足以辨明时归入签名或交换，否则保留 `unknown`。`DES / 3DES` 被拆成两个算法，`TripleDES` / `DESede` 对应 3DES。非公钥算法仍保留已有的逐行用途摆动消噪，避免 PBKDF2 在同文件重复报出。

真实公开样例复扫结果：`hybrid_crypto.js:13` 为 `ECC / key_exchange`，两家工具的证据均只指向第 13 行；`:104` 为 `ECDSA / EC / signing`，两家证据均只指向第 104 行。`crypto_samples.go:151` 的 DES 与 `:162` 的 3DES 也分别落在独立 Finding。35 条结果全部通过 v0.1 Schema；相关离线扫描自检 180 项通过。

## 对开发语料数字的影响

在相同的三套公开开发语料、相同标签和同一个 `benchmark/eval.py` 口径下重新执行完整快扫：

| | 修正前 | 修正后 |
|---|---:|---:|
| TP / FP / FN | 619 / 87 / 63 | **619 / 97 / 63** |
| Precision | 87.7% | **86.5%** |
| Recall | 90.8% | **90.8%** |
| F1 | 89.2% | **88.6%** |

分集 Precision：CryptoAPI-Bench 87.0%、CamBench_Cap 92.9%、LLM-CMT 86.2%。新增十个净 FP 来自原先被合桶的同文件公钥用途记录，或 DES/3DES 的分开报告。该基准的主标签只到 `(文件, 算法)`，不能单独验证这些用途记录的业务真实性；因此既不能把十条一概称为真实误报，也不能为了恢复旧分数而重新把签名与密钥交换证据混在一起。条件分支上的 `RSA-1024` 和公开项目中的 Ed25519 调用说明这里包含需要逐案解释的情况。

本结果是**开发集同数据复扫**，仍不能代替独立留出。修正后数值仍超过方案中的 P≥85%、R≥90% 数值门槛，但独立泛化和语义正确性尚未由此证明。旧的集成验收文档保留修正前的历史值，当前对外材料应引用本表。

```cmd
python benchmark\eval.py C:\Users\lenovo\acg_isolation_all.json --scanned cryptoapi-bench,cambench-cap,llmcmt
python scanner\selftest.py
python benchmark\eval.py --selftest
```

上述合并 JSON 是本机临时复扫产物，不随源码发布。公开样例能证明第 13/104 行和 151/162 行的证据隔离；三套开发集只能支持本页所列同口径指标。新的独立样本、AI 对这些用途的判断和修复方案仍需分别验收。
