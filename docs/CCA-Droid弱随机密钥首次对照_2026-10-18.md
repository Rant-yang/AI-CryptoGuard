## 结果

只评 `JAVA-WEAK-PRNG-KEY` 这一项：源文件中可达的弱随机数生成 AES 密钥。
5 个正例、2 个负例，同一份匿名源码与 jar 进两个模式。

| 指标 | 快速扫描 | 快速扫描 + CrySentry |
|---|---:|---:|
| TP / FP / FN / TN | 0 / 0 / 5 / 2 | **4 / 1 / 1 / 1** |
| Precision | 无正预测，未定义 | **80.0%** |
| Recall | **0.0%** | **80.0%** |
| F1 | 无正预测，未定义 | **80.0%** |
| 已挂载 CrySentry taint | 0 | **5** |
| 未唯一挂载的 taint 线索 | 0 | **1** |
| CrySentry 阶段 | — | `completed`，约 **6.8 秒** |

这证明：**CrySentry 对这一种 Java 数据流弱密钥问题产生了快扫没有的新真阳性**。
它不能证明全系统 Precision/Recall 达标，也不能与 25 例旧对照的算法 Finding
或 OWASP 的文件级哈希数据混算。

## 解析器修复后的同集回归（不是新的独立成绩）

首次结果中 `c002` 的 CrySentry 原始 `sourceStmt` **实际包含**
`<clinit>()>[4@L21]`；是本项目 `_SITE_RE` 的 `[^>]+` 在内层 `>` 处提前截断，
才丢失真实行号。修复为读取调用点位置括号前的最终 `>`，并用离线用例同时
验证 `<clinit>`、`<init>` 与没有 `@L` 时不猜行号。**没有根据源码内容推测行号。**

在同一份冻结的 7 文件、同一标签上的新目录复跑：快扫仍为 0/0/5；深扫
TP/FP/FN/TN 从 **4/1/1/1** 变为 **5/1/0/1**，P=83.3%、R=100.0%、F1=90.9%；
已挂载 taint 从 5 增至 6，未解决线索从 1 降为 0。弱随机分支不可达的 `c004`
仍是误报。本段只证明已知解析缺口的**同集回归**；对其他项目的泛化能力还需
新的未使用样本验证，首次 4/1/1 不得被改写。

## `c004` 误报的控制流核查

用同一 JDK 17 的 `javap -c -p holdout.c004.C004` 检查冻结 jar：`main` 中
`iconst_2` 后直接调用 `go(int)`；`go` 入口执行 `if_icmple 19`，只有参数不大于 1
才跳到 `Random.nextBytes` 与 `SecretKeySpec` 所在的偏移 19–47。因此当前 `main`
入口不执行弱随机密钥分支；首次和回归中的这 1 条 FP 都是真实误报。

CrySentry 给出的 source/sink 是**静态数据流候选**，本项目尚未实现通用的跨方法
常量传播和控制流可达性证明。不能为了这一个已见负例写文件名特判或一律删除
`Random → SecretKeySpec` 命中，否则会掩盖可达场景。现在这类新 Finding 带
`control-flow-unverified` 标签，页面显示“分支可达性未验证”，并提示用户核对
实际调用条件；**该标记不改变已记录的 TP/FP/FN**，也不声称误报已被消除。
