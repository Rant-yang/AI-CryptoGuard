# 缺陷类别覆盖核查（2026-10-19）

本表对照初始方案 §2.2 的“至少 15 类密码安全问题，其中密码/凭据管理相关不少于 8 类”。**规则 ID、算法名称、Finding 条数和独立缺陷类别不是同一个计数单位。**以下只核对代码与可运行自检；“有实现”不代表外部逐类准确率已通过，更不能用开发集总体 P/R 代替。

## 原方案建议的 17 类

| # | 类别 | 当前判断 | 可核查实现或缺口 |
|---:|---|---|---|
| 1 | 弱/废弃算法 | 已实现，外部范围有限 | CryptoScan/cbom-scan 经 `scanner/merge.py` 归一风险；自研 `scanner/adapters/local_literal.py` 补多语言字面量及 API。不同算法不是不同缺陷类别。 |
| 2 | AES-ECB 等不安全工作模式 | 已实现，部分参数形态未覆盖 | `scanner/adapters/local_literal.py` 的 R5/R6/R7/R10 与 `scanner/selftest.py` 的对应正负例。CryParBench/JobX 外部首测暴露 Java 参数传播缺口。 |
| 3 | 固定 IV | 未作为独立缺陷规则验收 | 当前可发现部分含 IV 的代码/线索，但没有稳定的“固定 IV”规则 ID、正负样例及逐类统计。不能把含 IV 的普通算法 Finding 算作检出。 |
| 4 | Nonce 重用/固定 Nonce | 未作为独立缺陷规则验收 | `PY-WEAK-RANDOM-CRYPTO` 可命中弱随机生成的 `nonce`，但弱随机不等于重用/固定；Chimera 修复案例也不证明本类已实现。 |
| 5 | 弱随机数 | 已实现，窄范围 | `scanner/adapters/python_ast.py` 识别直接赋给安全用途变量的 `random.Random().randbytes`；Java 深扫有可预测随机流入密钥构造的专门证据，且只给部分传播链。不能泛化到所有 PRNG。 |
| 6 | 硬编码密钥 | 已实现，独立精度未证实 | `CRED-HARDCODED-CRYPTO-KEY`；私钥 PEM 另有更具体的 `CRED-EMBEDDED-PRIVATE-KEY`，两者不能无条件当两类互斥风险。 |
| 7 | 硬编码 API Key/Token/Secret | 已实现，独立精度未证实 | `CRED-HARDCODED-TOKEN`；`CRED-HIGH-ENTROPY-SECRET` 是对这类秘密的补充检测方式，不能仅凭第二个 ID 算新的管理缺陷。 |
| 8 | 密钥长度不足 | **已新增窄范围确定性规则** | `PY-RSA-KEYSIZE-LT2048` 仅在 Python AST 证明 `cryptography` 的 `rsa.generate_private_key(key_size=<整数字面量>)` 且长度低于 2048 时报告。变量传播、Java 生成与旧签名验证均未覆盖；不是 RSA 的 Shor 风险。 |
| 9 | 不安全 Hash | 已实现，需按用途复核 | 上游算法风险及自研 `PY-HASHLIB-NEW-WEAK-HASH`；不能把非安全用途的 MD5 文件校验自动说成可利用漏洞。与 #1 在某些样本上重叠，正式类别计数要有互斥定义。 |
| 10 | 密钥复用 | 未实现 | 没有跨使用点识别同一密钥材料的可靠证据与验收。 |
| 11 | 生产/测试凭据混用 | 未实现 | 检出硬编码值不等于确认环境混用。 |
| 12 | 证书验证绕过 | 部分线索 | 上游配置/证书类别可能产生线索，但当前缺少同一规则的正负验收和运行路径确认，不能称完整检出。 |
| 13 | 不安全 TLS/SSL 配置 | 部分线索 | TLS 版本/证书等可进入 lead；TLS 配置出现不等于已协商脆弱套件。没有把所有配置线索当作风险 Finding。 |
| 14 | 密钥撤销/过期后仍被调用 | 未实现 | 需要生命周期与调用点证据，不能用证书到期字符串替代。 |
| 15 | 密码调用链异常 | 部分实现 | CrySentry Java 深度证据可提供来源与敏感 API 的部分链；不等于通用异常链判定或完整可达路径。 |
| 16 | 量子脆弱公钥密码使用 | 已实现，依赖用途核实 | RSA/ECC 等识别后由 `core/quantum_assessment.py` 评估 Shor 风险；有名称/构造证据不等于业务用途已知。 |
| 17 | PQC 迁移用途不匹配 | **防错约束已实现，检测旧建议未单列** | `core/rules/pqc_routing.py` 拒绝签名→KEM 等不相容路线；这是系统自己的建议安全门，不能再当作源码里独立检出的漏洞。 |

另有 `scanner/adapters/local_literal.py` 的**低 PBKDF 迭代数**（R4/R12，含边界与负例），这是原 17 项之外的一类参数误用，但不能拿它替代“固定 IV/Nonce 重用”等尚未完成的原目标。

## 八条凭据规则的计数边界

`scanner/adapters/credential_scan.py` 确有八个 `CRED-*` 规则，`scanner/credential_selftest.py` 用合成正负例验了八个 ID 和不保存原文的隐私要求。按缺陷机制审查时，至少有两个潜在重叠：

1. “敏感变量中的高熵秘密”通常是硬编码 Token/Secret 的**发现方法/候选**，不是由熵本身产生的新管理失误。
2. “源码内嵌私钥材料”是硬编码密码学密钥的特殊形态，但吊销/轮换流程更具体。能否作为独立类别需在分类法中先写清边界，同一真实样本不能无解释地在两个类别重复计数。

因此当前可以准确说“**八个凭据检测规则已实现并有合成回归；八个互不重叠的管理缺陷类别及其各自外部性能尚未证明**”。[凭据检测记录](凭据检测_2026-10-14.md)中的开发专项 P/R 与 ProwlBench 的凭据存在性二分类也不能证明八类逐项达标。

## 新增密钥长度规则的边界与回归

- 只报告新的 RSA 私钥生成调用，且 `key_size` 是调用处可见的正整数字面量 `<2048`。依据：[NIST SP 800-131A Rev.2](https://csrc.nist.gov/pubs/sp/800/131/a/r2/final)。
- 证据仅保存规则、API、行号和位数；不保存密钥或源码原行。评估层将其标为经典配置问题 `not_applicable`，AI 层在本地解释并引用 E1，不向云端发送这条确定性事实。
- 自检排除 2048 位、变量长度、别名重绑定、注释和字符串；真实公开样例 `crypto_samples.py` 的 1024 位调用在第 37 行形成独立 Finding，原先的 docstring 命中仍被过滤。网页与 HTML 报告显示“RSA 密钥长度不足”，不会与泛称“RSA”的量子风险卡混淆。
- 这项新增规则**不是**“密钥长度不足已普遍覆盖”的证据。它也不证明用户代码实际执行、生成密钥已经部署或该密钥用于签名。

## 截止前的可引用说法

可以说“已实现弱算法、ECB、部分弱随机、部分短 RSA 新密钥、不安全 Hash、低 PBKDF 迭代和八条凭据规则，并有量子风险/用途分派”。**不能**据此直接宣称“15 个独立缺陷类别均已外部验收”或“八类凭据各自达到总体 P/R 目标”。若正式材料保留“15 类/8 类”作为既定目标，须增加固定分类法、每类至少一个带真值的正例和负例、最终扫描命中及逐类结果；未完成的类别和交叉重叠要如实列为限制。
