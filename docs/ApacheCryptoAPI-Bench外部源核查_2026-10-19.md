## 核查对象

来源：[CryptoAPI-Bench/ApacheCryptoAPI-Bench](https://github.com/CryptoAPI-Bench/ApacheCryptoAPI-Bench)，检查的仓库提交为 `7cb0feac079471de21a85f369d03d250dba0b137`。外部仓库只克隆到本机项目外；未执行其中的 JAR，也未将第三方源码、二进制或原始标签并入本项目。

`ApacheCryptoAPI-Bench_detail_list.xlsx` 的 `all cases` 表有 **121 条**人工整理记录，字段包括项目、类别、上下文（密码/非密码/非漏洞）、类名、方法和部分行号。`apache_codes/` 内有 8 个 `*-sources.jar`，没有可直接扫描的平铺 `.java` 树。

先用类名**末段**去源 JAR 中找同名 `.java`/`.scala`：121 条中 **84 条有候选同名文件、37 条找不到**。再按表格项目与完整包/类路径复核，支持其中一条表格混用点号与斜杠的写法后，**84 条均有唯一候选源文件**；其中 75 条有单一数字行号、9 条没有。早期脚本把混写的第 57 行误计为“仅末段同名”，故曾记 83，现已纠正。

对 75 条数字行号只做机械核对：表格 `Error line` 字符串在对应源码行上原样出现 11 条，在前后两行内出现 3 条，其余 61 条无法按字面匹配。该列不少内容是描述而非源码片段，**不匹配不等于标签错误**；也不能据此声称行号可信。完整候选路径仍未逐例验证源码版本、方法、上下文与实际执行，不能把 84 条直接当成可用真值。缺失源码尤其集中在 `MessageDigest`（6 条中 5 条）和部分 `Random`、`CipherAlgo` 项。

## 对本项目评测的意义

该表主要标注 API 用途或误用上下文；本项目 Finding 的正式计数单位是 `(文件, 算法, 用途)`。原表并没有为所有案例给出稳定的算法名、用途枚举及同文件所有密码使用的完整负例清单。源码 JAR 还可能在一个文件里包含表格未标出的其他调用。直接扫描 8 个 JAR 的全部源码，再把未列出的检出统统计作 FP，会制造错误的 Precision；把 121 条直接当作完整同口径独立留出集也不成立。

它仍可用于**另行预注册的真实项目专项诊断**：先核对完整包名、源码版本与行号，再固定范围和逐实例匹配规则；只报告通过人工核对的那部分实例及该专项的分母。若用它作 Java 深度证据演示，也须明确第三方 CrySentry、样本来源以及 `partial` 污点证据的边界。该来源目前不替代仍缺的全系统同口径独立留出集。
