# 性能与有效性评测报告候选版（截至 2026-10-18）

本文件把**已测到的事实**与**尚未验证的目标**分开，是可供设计报告引用的
评测候选材料，**不是“全系统独立达标”的最终成绩单**。
Precision = TP/(TP+FP)，Recall = TP/(TP+FN)；计数单位、样本来源、标签定义和
首测/回归属性不同的数字不能合并或当作同一指标横向比较。下表中的“首次独立”
指该固定数据在用于本项目调参前的第一次扫描；看过错例后在原数据上的任何成绩
均标为“同集回归”。

## 对目标门槛的可引用结论

初期方案要求 **P≥85%、R≥90%**，开发语料 86.5%/90.8% 只说明已在该三套
已参与开发的公开数据上达到数值门槛。现有外部首次诊断分别检验 Java 弱算法、
Python 弱哈希或凭据秘密存在性，**没有一套与完整产品 Finding 口径完全一致的
预冻结独立留出集**。因此目前不能宣称“全系统独立 P/R 达标”，也不能从
Juliet 全正例的 100% 或 OWASP 同集回归的 100% 推出泛化效果。

八类凭据管理规则已实现，但开发凭据专项 69.3%/74.3% 与 ProwlBench 的
片段级 88.65%/23.46% 均不能证明八个细分类别各自达标。两套标签的任务不同：
例如 `localhost` URL 内嵌口令在上游“可用秘密”标签中可能为负例，在本项目的
“凭据写在 URL 中”定义下仍应报警。差异须按产品定义保留并逐案解释，不能为提分
直接删规则或挑掉困难样本。

另对 [Apache Kerberos 模块](Java深度真实项目验收_2026-10-18.md)完成了一次真实
第三方源码 jar + 编译 jar 的 CrySentry 深度运行：30 条已定位记录、23 条已挂载
证据（18 pattern / 5 taint）、45 条最终 Finding 通过契约；taint 均缺来源位置。
这是**运行与融合验收**，没有可比的独立 P/R，不计入上表成绩。
Apache 标签 121 条里只有 71 条可在附带源码 jar 中找到唯一源码；已运行模块
仅对应 36 条，而且标签行号与源码版本存在错位（见[Java 真实项目验收](Java深度真实项目验收_2026-10-18.md)）。
在逐调用点重定位和冻结同口径标签前，不把这次运行转换成 P/R。

## 时间与完成率

固定 25 例 Java 对照在本机重跑时，快速扫描约 0.7 秒，CrySentry 单独约 6.9 秒；此前同题记录约 5.8 秒。公开 `activemq` smoke 曾约 15 秒。它们只反映特定机器、项目与缓存条件，**不能证明“任意项目 30 秒内完成”**。深度模式还需用户先编译目标项目，编译时间没有计入扫描耗时。跨盘 classpath 暂存可能增加磁盘和时间开销。

Docker Compose 快速模式在本机完成了构建、健康检查、公开样例 Web 上传→真实扫描→结果→删除的闭环；这是**本机**部署证据，不是另一台机器的复现。系统 apt 包仍由上游仓库解析，不能声称全环境按字节锁定。

固定 25 例可比对照中深扫新增 16 条已定位 pattern 证据，P/R **未变化**。
另一个在扫描前冻结的 [CCA-Droid 弱随机密钥 7 例专项](CCA-Droid弱随机密钥首次对照_2026-10-18.md)
显示 CrySentry 在该种数据流上新增 4 个真阳性，同时有 1 个路径不可达误报；
它的标签和计数单位与前述 25 例不同，不能合并成一组“深扫总体”指标。
公开弱随机密钥演示的 taint 只有来源和汇点位置，标记 `partial`，不称为完整传播链。

## AI、修复与用户体验的分项验收

当前 TLS 规则修正后的公开样例固定 35 条 Finding（28 条算法、7 条凭据），
**35/35** 达到 `explained` 且通过 v0.2 契约；算法 28 条经模型处理，凭据 7 条
仅由本地规则处理。新输入的 28 条脱敏盲审包已生成，人工语义判断仍为 **0/28**。
这证明调用和输出结构可用，**没有** AI 用途、引用和整改建议的语义正确率。
旧版 30 条样本也是历史结构验收，不能与当前批次混算。详见
[TLS 修正规则与当前复验](TLS规则修正与AI复验_2026-10-18.md)和
[当前批次盲审操作](当前批次AI盲审操作_2026-10-18.md)。

Repair→Verify 的三类模板通过合成复扫及自建项目测试；
[Chimera nonce 第三方正向案例](第三方正向修复验证_2026-10-18.md)中，同一上游模块
45 条测试在临时补丁前后均通过。修复器自己的结果仍把项目测试标为 `NOT_RUN`，
那 45 条是独立容器命令的结果。其他两类模板的第三方正向案例、完整项目测试、
真实协议兼容性及实际部署未验证。报告只能称“候选补丁与已运行的验证”，
不能称“生产环境修复成功”。

## 当前不能宣称的指标或能力

- 尚无新的、与开发语料同计数单位、先封存后扫描的正式留出集；开发 P/R 达标不等于最终泛化达标。
- 25 例深度对照没有检测率提升。公开弱随机密钥演示产生一条 taint Finding，但仅有来源/汇点位置，`partial` 不等于完整传播路径。
- 当前 35 条公开样例虽 35/35 结构有效，但**人工盲审 0/28**，仍无语义通过率；旧版固定 30 条同样只有结构结果、人工审阅 0/30。不能把两批样本或结构通过率冒称 AI 语义正确率。
- Repair→Verify 三类模板通过合成复扫与自建项目测试；[Chimera nonce 第三方正向案例](第三方正向修复验证_2026-10-18.md)的同一模块 45 条上游测试在补丁前后均通过。全项目测试、真实网络协议及另外两类模板的第三方正向兼容性仍未验证；候选补丁不能自动部署。
- 8 类凭据管理缺陷已编码，但没有每类的独立留出证据；不能用“8 类规则”直接推出“8 类识别率达标”。

下一次正式评测应先写入样本来源、许可证、抽样种子、排除条件、匿名化映射保管方式、正负标签单位、未覆盖类别处理和固定版本哈希，再锁定样本。首次结果与后续针对错例的回归结果分别报告；任何失败、超时、skipped 计入完成率，不得作为零发现样本混入 P/R。
